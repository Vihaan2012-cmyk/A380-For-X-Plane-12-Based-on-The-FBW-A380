# AI first officer as Pilot Monitoring

Date: 22 Oct 2026. Crate: `crates/ai_fo` (own `[workspace]`, no dependencies). Status: the state machine
and its scenario tests are done; nothing is wired into the plugin yet.

Goal: the F/O does the full Pilot Monitoring job: standard callouts, checklists, cabin and ground
communication, ECAM procedures on the PF's order, ATC radio tuning and frequency changes, and MFD entries.
The existing extras (copilot, GSE, walkaround, cabin crew, FAP) keep working unchanged until the plugin
switches over.

## 3. SOP phases (`ai_fo::Phase`)

`Preflight -> TaxiOut -> TakeoffRoll -> Climb -> Cruise -> Descent -> Approach (-> GoAround) -> Rollout -> TaxiIn -> Parked`.

Airborne phases come from `FMGC_FLIGHT_PHASE` (FBW enum, 1/2 climb, 3 cruise, 4 descent, 5 approach, 6
go-around); when it is 0 or 7 the tracker falls back to vertical speed and radio height. Ground phases come
from engines running, TLA (FLX detent 34, as `copilot.rs`) and ground speed. Rollout ends below 30 kt with
reversers stowed; Parked when all engines are off after a flight.

Inputs are one `Snapshot` per frame (all plain values the plugin already reads in `copilot.rs`, plus VFE per
flap position, Vapp, pitch/bank, COM1 active/standby, the station list, the handover, the ECAM state and the
EFB's takeoff/approach data). The PF's spoken or keyed orders arrive as `PfCommand`s. The machine returns
`Vec<Action>`; it never touches the sim.

## 4. ECAM procedures

Data: `crates/fws_data` (FBW's `EcamAbnormalSensedProcedures` as static tables). Public types used:
`fws_data::procedure(id) -> Option<&'static Procedure>`, `Procedure { id, title, plain_title, items, .. }`,
`Item { name, kind: ItemKind::{Action, Condition, Plain}, sensed, level, label, time, .. }`.
`ai_fo::EcamItem` / `EcamProcedure` mirror those fields one to one; the plugin passes a
`fn(u32) -> Option<EcamProcedure>` that converts `fws_data::procedure(id)` (no dependency inside `ai_fo`).
The test fixture is the start of FBW's ENG 1 FIRE (260800005).

Sequence (`ecam::EcamRunner`):

1. A new warning: the PM reads the title (`ReadEcamTitle`) and waits. Nothing is done without the PF's
   `PfCommand::EcamActions`.
2. Each line in order. Sensed actions already complete are passed silently. Plain lines are read.
3. Action lines: read (`ReadEcam`), then by `ecam::doer`:
   - `Pf`: thrust levers, sidestick, rudder — the PF's own controls (the user flies with a TCA). The PM waits
     until the FWS senses the item done.
   - `Pm(Switch)`: engine master, fire push-button, agents, APU bleed / master / fire. Engine master OFF and
     fire push-button need the PF's `Confirm` first (irreversible items). The PM then emits `Switch`, and waits
     for the sensed completion; unsensed ones are ticked (`TickEcam`).
   - `Atc`: `AtcNotify` (the PM transmits) and tick.
   - unsensed and not mapped: ticked after reading. Sensed and not mapped: read, then wait for sensing.
4. `time` on an item: due that many seconds after the previous line completed (agent 1 after 10 s, the
   "still fire" check after 30 s, as FBW's data has them).
5. Conditions: true (sensed by the FWS) -> read and do the deeper lines; false -> skip every line with a higher
   `level`.
6. End: "ECAM actions complete". The procedure is dropped if the warning clears.

Plugin wiring (next step): `Switch` -> the existing overhead variables the deep model reads
(`ENG_MASTER`, fire push-button and agent L:vars, `OVHD_PNEU_APU_BLEED`, APU master); `EcamLive.done` from the
native FWS (`crates/fws`) item states; `TickEcam` -> the ECL item check the EWD shows. Grow the `doer` table
by counting which `fws_data` action items are still `Unmapped` (a test that lists them per ATA chapter).

## 5. ATC radio

- Station list per frame (`Snapshot.frequencies`): online controllers when connected
  (`crates/datalink/src/online.rs`: `OnlineAtc { callsign, frequency_mhz, kind: AtcKind, .. }`, `nearby(..)`;
  the plugin's `src/atc_online.rs` `Station` already powers the EFB ATC page), else the airport's own
  frequencies from navdata (`src/navdata/apt.rs` `Frequency { kind, khz }` from apt.dat 1050-1056): the
  departure airport on the ground and in climb, the destination in descent. `AtcKind`/apt.dat kinds map to
  `StationKind` (Delivery, Ground, Tower, Departure, Approach, Centre, ATIS).
- Preselect (`radio::next_kind`): taxi -> tower, takeoff -> departure, climb -> centre, descent -> approach,
  approach -> tower, rollout -> ground. Only standby is touched; never the active frequency.
- Handover (`Snapshot.handover` with a sequence number, from the sim's ATC or a PF "contact X" command):
  readback, tune standby if needed, swap. Out-of-band frequencies are refused ("unable").
- Output `TuneStandby { com, khz }` / `SwapCom(com)` go through the native RMP (`crates/rmp`:
  `pack_bcd32_hz`, `VhfRadioUnit`) so the RMP display and the sim radios stay in step.

## 6. MFD entries

`crates/fms/src/service.rs` `Command` covers flight-plan edits only (city pair, runways, procedures,
waypoints, constraints, cruise steps). It has no PERF or wind entry today. Plan:

- Flight-plan items the PM may enter on command go through `Fms::execute(db, Command::..)`
  (e.g. `SetDestinationRunway`, `SetApproach`).
- `MfdEntry::Takeoff` (flaps, V1, VR, V2, flex temp, THS) and `MfdEntry::Approach` (QNH, temp, wind,
  BARO/RADIO minimum) need a small perf-entry API next to the native FMS (owner: the fms / fms_perf agent);
  until then the plugin writes the same values the MFD PERF page writes.
- Sources: the EFB's takeoff calculator (already sent as `copilotTakeoffFlaps`) and the destination ATIS /
  METAR the datalink crate fetches.

## 8. User controls (EFB)

User rule: realism ships always on; settings exist only for preferences and assists. Who does a PM job is an
assist (a solo pilot may want to do it), so these are settings. How the F/O does it (thresholds, the order of
ECAM lines, confirmation of irreversible items) is not a setting.

- One "First officer" group: `Duties { callouts, flows, checklists, ecam, radios, cabin, ground, mfd }`, all on
  by default, plus the `auto_gear_up` assist (off). Map the existing keys: `copilotCallouts` -> callouts,
  `copilotAfterStart`/`copilotAfterLanding` -> flows, `copilotAutoChecklists` -> checklists,
  `copilotGearUp` -> auto_gear_up, `copilotMode` -> all on. `copilotSop` folds into callouts (realism).
- Voice (`copilotVoice`) and checklist reading mode stay as preferences.
- PF commands: X-Plane commands `fbw/fo/<command>` (gear up, gear down, flaps up/down one step, go-around
  flaps, ECAM actions, confirm, checklist, contact next, push, start, disconnect, enter takeoff/approach data)
  so they can be bound to TCA buttons or VR, plus buttons on the EFB F/O panel.

### Tool and output

`tools/fo_voices/build.py <repo> <models> <out>` (venv and models in `E:/fbw-build/tts`). It imports
`tools/copilot_voices.py` for the callout and EFB checklist tables, so the old Piper script still works but is
superseded. Output: `<out>/<voice>/fo_<key>.wav`, 22.05 kHz mono 16-bit (what `voice_pack::parse_wav` takes),
`<out>/manifest.json` (text, kind, position and length of every key per voice), `<out>/samples/<voice>/` (10
review lines including one assembled readback). Processing: high-pass 140 Hz, low-pass 6.8 kHz, trim at
-40 dB (12 ms pad for building blocks, 40 ms for whole lines), tanh soft limit, peak -3 dBFS (all GENERIC).
Reruns skip files that exist; delete a voice folder to regenerate it.

ECAM text is spoken from FBW's titles and item names only, through an abbreviation table (ENG -> engine,
P/B -> push button, L/G -> landing gear, ...); unknown short tokens without vowels are spelled letter by
letter. Digit 9 is "niner" in the blocks (radiotelephony), "nine" inside ECAM text.

### Runtime assembly

Readbacks are built from blocks, never synthesised at runtime:

- Frequency `khz` (from `Action::ReadFrequency`): `stn_<kind>`, then each MHz digit `d<n>`, `w_decimal`, then
  the kHz digits with trailing zeros dropped (at least one), the last one as `d<n>_end`.
  121 500 -> `stn_tower d1 d2 d1 w_decimal d5_end`; 118 005 -> `... d1 d1 d8 w_decimal d0 d0 d5_end`.
- Flight level: `w_fl` + three digits (`fl 350` -> `w_fl d3 d5 d0_end`).
- Heading: `w_heading` + three digits. Speed: `w_speed_w` + digits. Squawk: `w_squawk` + four digits.
- Altitude: thousands as digits + `w_thousand`, then a hundreds digit + `w_hundred` if non-zero (12 500 ->
  `d1 d2 w_thousand d5 w_hundred`).
- Plugin side (next step): `copilot::say_seq(&[&str])` queues one item whose PCM is the blocks concatenated with a
  30 ms gap (all files share one format), so the 0.25 s gap between queue items does not split a readback.
  `voice_pack::load_copilot` loads every `fo_*.wav` of a voice into memory; with the ECAM set this is
  much larger than before, so `e_*` and `t_*` should be read from disk when queued.
