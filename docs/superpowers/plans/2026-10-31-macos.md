# macOS support

Goal: the aircraft flies in X-Plane 12 on a Mac with working screens, sounds and systems, and installs from a Mac installer. Apple Silicon first, Intel in the same universal binaries. X-Plane 12.4.4 or newer, because the screen routes below need SDK 4.4.0.

Not in scope: the authoring tools (`msfs2xp-aircraft`, the GP7200 chain, the release scripts) stay on Windows. They produce platform-neutral files. `a380_displays` (native Skia screens) waits, because the shipped screens are Chromium.

## Fastest route

Route A below with the systems inside the plugin, so a Mac install is one `mac.xpl` plus the existing aircraft files:

- Keep: browser devices for all pages, a JavaScript SimVar shim, `remote::Systems::Local`, the pages served by the plugin's HTTP server.
- Skip for the first release: XPHFBW, the systems server and POSIX transport, Steam Audio, the installer, notarisation (a zip and a quarantine command, as a beta).
- Add back later only if measured or asked for: the server if a systems crash or frame time needs it, then the installer and signing.

Stages 0, 1, 2 and the route A part of 3 are the whole path to a first flight. If stage 0 shows route A is too slow, this shortcut is gone and the route B work returns.

## Where it stands, measured 31 Oct

| Part | State |
|---|---|
| Rust plugin, `--features js` | `cargo check --target aarch64-apple-darwin --lib`: 0 errors. C and C++ were stubbed for this check, nothing was linked or run |
| Crates | Pass on Linux (`2026-10-22-linux.md`), so little is tied to Windows in the logic |
| OBJ, DDS, PNG, `main.lua`, FMOD banks | Portable files |
| SASL | `plugins/sasl/64/mac.xpl` already ships, universal (x86_64 + arm64) |
| SDK | 4.4.0-b1 in `D:/A380/SDK`; its `XPLM.framework` is universal. The installed X-Plane is 12.4.4. The plugin does not use the 4.4.0 APIs yet |
| Installer | Electron `package.json` has `win` and `linux` targets, no `mac`. `installer/src/install.rs:339` finds SASL by `64/win.xpl` |

It compiles because Windows calls have do-nothing stand-ins. On a Mac today it would load and do nothing:

- `src/xp.rs`: `LoadLibraryA`/`GetProcAddress` return null and `xplm_symbol` asks for `XPLM_64.dll`, so no X-Plane API at all. The same stand-ins are copied into `sensors.rs`, `start_state.rs` and `failures.rs`.
- `src/display/gl.rs`: loads only `opengl32.dll` and `wglGetProcAddress`.
- `src/remote/win.rs`, `src/xphfbw_bridge.rs`: shared memory, events and mutexes are stand-ins, so XPHFBW could not connect.
- `app/`: Windows only. `gpu_share.rs` and `views.rs` use D3D11, `tray.rs` and `crash.rs` use Win32, `chromium_fix.rs` patches `libcef.dll`, the launcher starts `XPHFBW.exe`.
- `src/sound_levels.rs`, `src/binaural.rs`: no FMOD access off Windows; Steam Audio ships only as DLLs.
- `src/diag.rs`, `src/perf.rs`, `src/big_stack.rs`: Windows process stats and stack handling.
- Paths: the plugin never enables `XPLM_USE_NATIVE_PATHS`, so X-Plane would hand it `Macintosh HD:Users:...` style paths.

## Metal and the screen routes

There is no raw Metal API: the SDK exposes no device or command buffer, and hooking X-Plane's internals is not an option. SDK 4.4.0 does give two routes that need no plugin OpenGL. Its header calls the OpenGL route "the legacy OpenGL bridge" and panel graphics "native". On a Mac X-Plane renders through Metal, so native should mean Metal; no document found says so outright, and none states the Mac behaviour of these APIs. All of this comes from reading headers, nothing has been run.

| Route | How frames arrive | Gains | Costs |
|---|---|---|---|
| **A. X-Plane's browser device** (`xplm_WindowContentTypeBrowser`) | X-Plane's own CEF renders the page and copies it to the device | No XPHFBW on Mac: no app bundle, helpers, Chromium notarisation or frame transport | Pages only reach the plugin through async `xplane.<name>()` calls and `XPLMAvionicsInjectScript`, JSON on the main thread |
| **B. XPHFBW + panel graphics** (`xplm_WindowContentTypePanelGraphics`, `XPLMCreateTexture`) | Our Chromium's pixels become a texture each frame, drawn with a mesh | Keeps the current page bridge, no GL | All of the XPHFBW port. Whole textures, no dirty rectangles (tile them). Bilinear, no mips, so the `draw_bridge` shader goes and filtering moves into the page or the app |
| **C. XPHFBW + OpenGL bridge** | IOSurface wrapped by `CGLTexImageIOSurface2D`, or pixel uploads | Closest to today's `gl.rs` | Depends on the part of X-Plane its own header calls legacy, on a driver Apple deprecated in 2018 |

Choice: try A first, B is the fallback, C only if both fail. The hard part of A is that FlyByWire's pages read SimVars synchronously from shared memory (`xphfbw_bridge.rs`). There they would read a JavaScript cache that the plugin refreshes each frame, for up to 19 pages. Whether that is fast enough is the question stage 0 answers.

### No XPHFBW app on route A

XPHFBW does several jobs. On route A a Mac needs no app, and each job has a home:

| Job today | On a Mac |
|---|---|
| FlyByWire's Rust systems, in lockstep over shared memory | `fbw_a380_systems_server`: already a headless process with no Chromium and no window. `start_systems` already falls back to it, then to the plugin |
| Screen pages | X-Plane's browser devices |
| `SystemsHost` and `ExtrasHost`, FlyByWire logic in screenless 1x1 pages | Hidden browser devices if they keep running undrawn, otherwise promote the native versions, which only shadow the JS today (`native_systems_host.rs`) |
| EFB and settings page, `web.rs`, `scheme.rs` | Browser device and `XPLMWindowSetURL` window, served by the plugin's HTTP server |
| `renderer.rs` V8 bindings | A JavaScript shim over `xplane.*` |
| Tray icon | Dropped |

This only holds if route A works. On route B or C Chromium still has to run outside X-Plane, and CEF requires an app bundle on a Mac, though `LSUIElement` keeps it out of the Dock.

## Needs from outside the code

1. **A Mac** from stage 2 on. GitHub's macOS runners can build and run offline tests, but cannot run X-Plane. Apple Silicon, 16 GB or more, with X-Plane 12.4.4 or newer (the demo is enough for the first stages).
2. **Workflow scope on the GitHub token** for Actions (`gh auth refresh -s workflow`); the token has lacked it so far.
3. **Apple Developer ID (99 USD a year)**, decided by stage 6. Without notarisation every user has to clear quarantine by hand.

## Stages

Each stage ends with something checkable. Unix code goes behind `cfg(unix)` wherever Linux can share it.

### 0. Pick the screen route, on the Windows PC (small)

No Mac needed: the same APIs exist in the installed X-Plane.

- Run in the Mac's shape: XPHFBW off, `fbw_a380_systems_server` running the systems.
- Browser device showing the real SD and PFD pages, fed by a JavaScript SimVar cache over `xplane.*`, served from the plugin's local HTTP server.
- `SystemsHost` and `ExtrasHost` on hidden browser devices: do they keep running when nothing draws them?
- Panel graphics device showing a 768x1024 frame from `XPLMCreateTexture` every frame, for route B.
- Measure main-thread time per page, update rate and memory against XPHFBW, then scale to all 19 devices.

Done when: a route is chosen on numbers. Also record whether route A would suit Windows, since it would remove the separate Chromium process.

### 1. Build on a Mac without owning one (small)

- GitHub Actions job on `macos-14`: build both architectures, `lipo` into `64/mac.xpl`, run the crate and library tests.
- Real C++ build of the FADEC and computer sources in `build.rs` with Apple clang.
- Replace the hard-coded `E:/` oracle paths that still make tests skip.

Done when: CI is green and `lipo -info` shows both slices.

### 2. The plugin loads on a Mac (small to medium)

- One `dynlib` module (`dlopen`/`dlsym`, `RTLD_DEFAULT` for XPLM) replaces the copied stand-ins.
- Enable `XPLM_USE_NATIVE_PATHS` in `XPluginStart`.
- Link as a bundle with undefined XPLM symbols resolved at load. Check stack use in place of `big_stack.rs`.
- Systems in the plugin for now (`remote::Systems::Local`), so this stage needs no POSIX transport.
- First check on the Mac: the chosen route's device actually works there, before building on it. If it does not, fall to the next route.

Done when: X-Plane loads the aircraft, `Log.txt` shows the systems ticking, flight controls and SASL animations work, one test device shows the chosen route.

### 3. Screens (route A medium, route B large)

**Route A:**
- `remote/posix.rs` in place of the 185-line `remote/win.rs`: `shm_open`, `mmap`, events and process watching (see route B below for the Mac limits). Build `fbw_a380_systems_server` for Mac and start it from `start_systems`.
- All pages on browser devices with the SimVar cache, Coherent shim and input routed through `xplane.*`.
- `web.rs` and `scheme.rs` move into the plugin's HTTP server; the EFB and settings page load from it.
- `SystemsHost` and `ExtrasHost` as stage 0 decided.
- `ATTR_cockpit_device` screens keep their device IDs.
- Filtering by CSS scale in the page, since the shader in `gl.rs` is not in this path.

**Route B or C:**
- `remote/posix.rs`: `shm_open` and `mmap` for `Shared` (31-character name limit on Mac), process-shared `pthread` condition variables or a Unix socket for events (Mac has no `sem_timedwait`), `kill(pid, 0)` and `posix_spawn` for the process.
- CEF 152 macOS runtime in `XPHFBW.app`: the framework under `Contents/Frameworks`, Helper bundles for the GPU, Renderer and Plugin processes, framework loaded at run time, entitlements for JIT.
- Check the `v8 =152.2.0` prebuilt for both architectures and the `gn_root` junction workaround's Unix equivalent.
- Compile out `chromium_fix.rs`, `gpu_share.rs` and the D3D11 half of `views.rs`. Use CEF's software `OnPaint`, the same BGRA and dirty-rectangle `ScreenBlock` route the Windows settings already use with `sharedTextures` off.
- Route C only: load `OpenGL.framework`, and make `gl.rs`'s function table tolerate gaps (`glBindVertexArray` is `APPLE`-suffixed in the legacy profile, swizzle is missing).

Done when: every screen boots and updates in the sim, touch and mouse input reach the pages, and restart after a crash works.

### 4. Sounds and the rest (medium)

- FMOD through `XPLMGetFMODStudio` in `sound_levels.rs`, `binaural.rs` with `libphonon.dylib` and `libphonon_fmod.dylib`.
- PDFium dylib for the EFB charts and documents, `pdf.rs` already has a `cfg(unix)` loader.
- `diag.rs` and `perf.rs` process stats with `ps` and `proc_pid_rusage`; one-launch diagnostics must still produce a full bundle.
- `fbw_a380_systems_server`: Mac build, or drop the fallback on Mac.
- Audit asset references for exact case, for case-sensitive volumes and Linux alike.

Done when: the full sound pack plays, charts open, the diagnostics bundle is complete.

### 5. Performance (open-ended)

- Measure first: frame time, memory and screen update rate on an M-series Mac with the 2K texture pack.
- 8 and 16 GB machines: unified memory is shared with X-Plane, so check Chromium's total and default the texture pack to fit.
- Check X-Plane's handling of our DDS formats on Apple GPUs.

Done when: a reasonable number agreed from those measurements holds on an approach at a big airport.

### 6. Installer and release (medium)

- `mac` target in the Electron installer (universal DMG), the X-Plane folder picker, `install.rs` finding SASL regardless of platform and installing `64/mac.xpl`.
- Sign and notarise `mac.xpl`, `fbw_a380_systems_server` and the installer, plus `XPHFBW.app` on route B or C: hardened runtime, every nested binary signed, stapled.
- Release assets from CI as a separate Mac runtime pack. Keep the privacy scan on everything published.
- README and known-issues page for Mac.

Done when: a clean Mac installs from the published DMG with no manual steps and flies a full circuit.

## Main risks

1. **Route A's data path.** Thousands of SimVars over async JSON on the main thread may be too slow. Stage 0 measures this on the existing PC before any Mac work.
2. **New APIs on Mac.** SDK 4.4.0 is new and the documents do not state Mac behaviour for the browser device or panel graphics. Stage 2 checks this first.
3. **The screenless JS hosts.** If `SystemsHost` and `ExtrasHost` stop when undrawn, the native versions must take over for real, and they have only run in shadow.
4. **Chromium's cost on a Mac.** Many pages on memory shared with X-Plane. Stage 5 may force a lower default scale on small machines.
5. **Testing distance.** Each stage from 2 needs in-sim runs. A remote tester makes the loop slow, which is why owning a Mac matters most.

## Order against Linux

Stage 0 applies to Linux too, and stages 1 and 2 are shared Unix work. Linux has no notarisation and WSL already runs the offline tests, so it should ship first or alongside.
